# 07 · 冷启动策略（Cold Start）

> 推荐系统的鲁棒性，看它怎么对待"没有历史数据的新用户"。
> 本文件定义：当 UserProfile 为空 / `order-list` 无历史 / 新门店无个性化信号时，如何降级出一个仍然靠谱的推荐。

## 一、冷启动的三种触发场景

| 场景 | 判定 | 缺失的信号 |
|---|---|---|
| **新用户冷启动** | `order-list` 为空或极少 | 无复购、无口味画像、无价格锚点 |
| **新口味/新场景冷启动** | 有历史但本次场景前所未有（如首次外送/首次聚餐） | 该场景无偏好证据 |
| **系统冷启动** | 画像丢失且暂时拿不到历史 | 临时无记忆 |

## 二、降级召回链路（Fallback Recall）

当个性化召回（R1 复购 / R2 偏好）无料时，按下列优先级补位：

```
缺个性化信号时的召回优先级：
  1. 时段驱动   —— now-time-info 判断早餐/正餐/下午茶/夜宵，召回该时段主推
  2. 热门驱动   —— query-meals 的「人气热卖」分类 + frequent 字段(门店常点)
  3. 优惠驱动   —— query-store-coupons / campaign-calendar 当前最划算的
  4. 时令/新品 —— campaign-calendar 的当季活动与上新
```

这样即便对一个全新用户，也能给出"当下这个点、这家店、最值得点"的合理推荐。

## 三、最小提问原则（Progressive Profiling）

冷启动时不要一次问一堆问题，**最多问 1 个最有信息量的问题**，边用边补画像：

- 优先问能一刀切召回空间的问题。决策树示例：
  ```
  不知道任何信息时，优先问一个：
    "就你一个人，还是几个人一起？大概想花多少？"   （一次锁定 人数 + 预算带）
  若用户只给了预算：
    直接按预算带 + 时段 + 热门 推，不再追问，先给方案再微调
  若用户说"随便/你决定":
    直接给"当前时段 + 热门 + 最划算"的稳妥一餐，并说明这是通用推荐
  ```
- 原则：**先给出可用的推荐，再在交互中逐步精细化**，而不是先盘问再推荐。首轮体验决定留存。

## 四、冷启动 → 热启动的过渡

- 用户每做一次选择/反馈，就把信号写入 UserProfile（05），画像从空白开始累积。
- 通常 1–2 轮交互后即可退出冷启动：拿到人数、预算带、一次口味选择后，就能切回个性化召回。
- 冷启动期的推荐要**显式说明**："还不太了解你，先按当前最稳的给你推，吃几次我就懂你了。"——坦诚会提升信任。

## 五、冷启动期的权重调整

- 个性化维度（f_taste/f_novelty）数据不足 → 降权，取中性 0.5。
- 相应抬升 f_value（性价比）、f_scene（场景适配）、f_benefit（优惠），这些不依赖历史也能算。
- 热量等显式约束（若用户主动提）照常生效。

## 六、与其它模块的接口

- 退出条件满足后，交还给正常 Pipeline（01）。
- 冷启动期间产生的所有选择 → 回写画像（05），为下次热启动铺路。
- 冷启动决策同样记入快照（08），标注 `mode: cold_start`。
