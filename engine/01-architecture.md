# 01 · 推荐系统架构总览（Architecture）

> 本文件定义「麦麦决策官」的推荐系统主干：一次推荐从用户开口到给出决策，内部经过哪些阶段、数据怎么流、每个阶段调用哪些麦当劳 MCP 工具。
> 这是整个 `engine/` 的骨架，其余文件是各阶段的细化。

## 一、设计哲学

把工业界推荐系统的标准范式 **「多路召回 → 统一精排 → 业务重排」** 搬进点餐场景，并补齐三个让它成为"系统"而非"脚本"的要素：

1. **有记忆**：用户画像持久化（见 `05-user-profile.md`），跨轮累积。
2. **有闭环**：反馈驱动下一轮，带探索与利用（见 `06-feedback-ee.md`）。
3. **可审计**：每次推荐产出决策链路快照（见 `08-decision-trace.md`）。

一句话：**不是"查菜单给选项"，而是"用一套可复现、可解释、会学习的推荐系统替用户做决策"。**

## 二、总体数据流（Pipeline）

```
         ┌─────────────────────────────────────────────────────────────┐
         │                       用户一句话请求                          │
         └─────────────────────────────────────────────────────────────┘
                                     │
   ┌─────────────────────────────────▼─────────────────────────────────┐
   │ ① 特征层 Feature Layer                                              │
   │   · 显式特征：从对话抽取(人数/预算/场景/口味/热量/赶时间/心情)      │
   │   · 隐式特征：读用户画像卡 UserProfile（05）                        │
   │   · 实时上下文：now-time-info（时段）、积分、券池                   │
   │   冷启动分支：无画像/无历史 → 走 07-cold-start                      │
   └─────────────────────────────────┬─────────────────────────────────┘
                                     │  Feature Vector + Context
   ┌─────────────────────────────────▼─────────────────────────────────┐
   │ ② 召回层 Recall（多路并行，见 02）                                  │
   │   R1 历史复购召回   R2 偏好匹配召回                                  │
   │   R3 优惠驱动召回   R4 新品探索召回(EE)                              │
   │   → 融合去重 → 候选集 Candidates（限 query-meals 真实在售边界）      │
   └─────────────────────────────────┬─────────────────────────────────┘
                                     │  Candidate Set (N 个可行方案)
   ┌─────────────────────────────────▼─────────────────────────────────┐
   │ ③ 精排层 Ranking（见 03）                                           │
   │   对每个候选算 6 维归一化分 → 按场景权重向量加权 → score ∈ [0,1]    │
   │   硬约束过滤：忌口 / 预算硬上限 / 热量红线                           │
   └─────────────────────────────────┬─────────────────────────────────┘
                                     │  Ranked List (score 降序)
   ┌─────────────────────────────────▼─────────────────────────────────┐
   │ ④ 重排层 Rerank + 解释（见 04）                                     │
   │   · 多样性重排（避免 Top3 高度同质）                                │
   │   · 优惠/过期资产兜底置顶                                           │
   │   · 生成 Reason code + 反事实解释(为什么没推 X)                     │
   └─────────────────────────────────┬─────────────────────────────────┘
                                     │  Top-3 + 解释
   ┌─────────────────────────────────▼─────────────────────────────────┐
   │ ⑤ 核价下单层 Order                                                  │
   │   query-store-coupons → calculate-price(真实券后价)                 │
   │   → create-order → query-order                                     │
   └─────────────────────────────────┬─────────────────────────────────┘
                                     │
   ┌─────────────────────────────────▼─────────────────────────────────┐
   │ ⑥ 反馈层 Feedback（见 06）                                          │
   │   用户"换/太贵/吃腻/就它了" → 负/正反馈 → 回写画像(05) → 下一轮      │
   └─────────────────────────────────────────────────────────────────┘

   ※ 全程旁路输出：决策链路快照 Decision Trace（见 08）
```

## 三、各层职责与 MCP 工具映射

| 层 | 职责 | 主要 MCP 工具 | 细化文档 |
|---|---|---|---|
| ① 特征 | 构建"用户+场景"特征向量 | `order-list`、`query-my-account`、`query-my-coupons`、`now-time-info` | 05 |
| ② 召回 | 多路生成候选 | `query-nearby-stores`/`delivery-*`、`query-meals`、`campaign-calendar` | 02 |
| ③ 精排 | 量化多目标打分 | `list-nutrition-foods`、`query-meal-detail` | 03 |
| ④ 重排 | 多样性+可解释 | （纯逻辑，无新增调用） | 04 |
| ⑤ 核价下单 | 真实价+闭环 | `query-store-coupons`、`calculate-price`、`create-order`、`query-order` | — |
| ⑥ 反馈 | 学习与记忆 | （回写 UserProfile） | 06 |

## 四、关键不变量（Invariants）

无论链路怎么走，这些底线永远成立：

1. **召回边界硬约束**：只有 `query-meals` 当前真实在售的 productCode 才能进入候选。接口没返回的，不推。
2. **价格以 `calculate-price` 为准**：展示给用户的到手价必须经真实核价，不得用菜单价推算券后价。
3. **券可用性以 `query-store-coupons` 为准**：`query-my-coupons`（卡包）只用于"规划/提醒"，承诺"这单能用"必须用门店券接口确认。
4. **可解释强制**：每个最终方案必须带 Reason；至少对主推给出一条反事实解释。
5. **决策可追踪**：每次推荐可输出一份 Decision Trace（08），说明候选规模、过滤项、精排 Top、重排理由。

## 五、运行模式（供 SKILL 主纲调度）

- **Full 模式**（默认）：完整走 ①~⑥，适合"帮我决定吃啥"。
- **Fast 模式**：用户明确"老样子/就上次那个" → 画像命中后跳过精排细节，直达核价下单。
- **Explore 模式**：用户"给我来点新鲜的" → 提高 R4 新品探索召回占比 + EE ε 调大（见 06）。
- **ColdStart 模式**：无画像/新用户 → 走 07。
