# 02 · 分层多路召回（Recall）

> 召回层的任务：从"当前门店真实在售菜单"这个全集里，快速捞出一批**值得进入精排**的候选方案（单品或套餐组合）。
> 用多路并行召回，各管一个视角，最后融合去重。这样既保证相关性（像用户、像场景），又保证惊喜度（新品探索）。

## 一、召回全集与硬边界

- 召回全集 = `query-meals(storeCode, orderType, beType)` 返回的当前门店、当前时段**真实在售**餐品/套餐。
- **硬边界**：任何不在该返回集合里的 productCode 一律不得进入候选。这是防"推荐了点不到的东西"的根本保证。
- 候选粒度：
  - **单品**（如板烧鸡腿堡 1406）
  - **官方套餐**（如板烧鸡腿堡三件套 9900005462）
  - **自由组合**（主食 + 小食 + 饮品，由召回层拼装，受预算/场景约束）

## 二、四路召回策略

### R1 · 历史复购召回（Repurchase Recall）
- 来源：`order-list` 解析出的高频商品/组合。
- 逻辑：统计近 N 单里出现频次 top 的 productCode 与搭配模式（如"主食+玉米杯""四件套"）。
- 作用：命中"老朋友的安全感"，复购是最强的正反馈信号。
- 产出示例：板烧鸡腿堡、双层吉士随心配、人气超值四件套。

### R2 · 偏好匹配召回（Preference Match Recall）
- 来源：UserProfile 口味向量（05）+ 本轮显式口味。
- 逻辑：按口味标签（鸡/牛/鱼/素、辣/不辣、咖啡控…）从菜单筛同类目候选，即使没买过也召回。
- 作用：扩展到"你没点过但符合你口味"的项，缓解复购导致的信息茧房。

### R3 · 优惠驱动召回（Deal-Driven Recall）
- 来源：`query-my-coupons` + `query-store-coupons` + `query-my-account`（将过期积分）+ `campaign-calendar`。
- 逻辑：把"手里的券能抵的商品""今日/近期到期券""可消耗将过期积分的兑换"直接作为高优召回。
- 作用：性价比与"防浪费"维度的候选来源。**今日到期券命中的候选，天然带重排加权（见 04）。**

### R4 · 新品探索召回（Exploration Recall / EE）
- 来源：`query-meals` 里带「上新/新品」标签的项 + `campaign-calendar` 的新品活动。
- 逻辑：按 EE 策略（06）以概率 ε 注入 1 个"用户没吃过、但与口味向量相近"的新品。
- 作用：打破茧房、制造惊喜、收集新偏好信号。必须在解释里**显式标注这是探索项**。

## 三、融合与去重（Fusion）

多路召回结果合并为统一候选集，规则：

1. **去重**：同一 productCode / 等价组合只保留一条，但记录它被哪些路召回命中（`recall_sources`）——命中多路的候选更可信。
2. **打召回标签**：每个候选携带来源标签，供精排/解释使用：
   `{repurchase, preference, deal, explore}`。
3. **规模控制**：候选集控制在 ~8–15 个，过多浪费精排、过少损失多样性。
4. **多路加权**：被 ≥2 路召回命中的候选，在精排前给一个小的先验加成（prior boost），因为"又像你又划算"通常是好答案。

## 四、召回结果数据结构（传给精排）

```json
{
  "store": { "storeCode": "1990262001", "beType": 1, "orderType": 1 },
  "candidates": [
    {
      "id": "combo_board_set",
      "type": "combo",
      "items": [{ "productCode": "1406", "name": "板烧鸡腿堡", "qty": 1 }],
      "menu_price": 24.0,
      "recall_sources": ["repurchase", "preference"],
      "tags": ["鸡肉", "人气"]
    }
  ]
}
```

## 五、与其它模块的接口

- **上游**：特征层给 UserProfile + 显式特征 + 门店。
- **下游**：候选集 → 精排（03）。
- **冷启动**：无 `order-list` 历史时，R1 退化为空，自动加大 R3（优惠）+ 热门召回，详见 07。
